# CPL specification decisions, edition 0.1

Every `Decision:` and `Design conflict:` line in the specifications
carries a project-wide stable identifier `[D-nnn]`, assigned in document
order (`grammar.md`, then `semantics.md`, `toolchain.md`, `stdlib.md`) and
in each document's reading order. The identifier never changes once
assigned; a new decision takes the next free number regardless of where it
is inserted, and a withdrawn decision keeps its row marked withdrawn. Each
document also keeps its own local numbering (`D1`..`D74` in the grammar,
`S1`..`S83` in the semantics, `T1`..`T82` in the toolchain, `S1`..`S48` in
the standard library, `C1`..`C39` in `cabi.md`, `P1`..`P11` in
`python.md`; the two `S` series are
distinct, and other documents write `stdlib.md S<n>` for the library's),
shown in the second column so that existing cross-references stay
readable.

This table is a review index, not a replacement for the decision text: the
rule and rationale columns are one-sentence condensations, and the full
statement, with its rejected alternatives, is at the cited section. Where a
decision records a *design conflict* (an internal inconsistency of
`design-doc.md`), the rule column begins with "Design conflict:".

Precedence used by the consistency pass of 2026-10-28 when two documents
disagreed: `design-doc.md`, then `grammar.md`, `semantics.md`,
`toolchain.md`, `stdlib.md`, except that a later document wins where the
earlier one is silent. Ownership boundaries that the pass fixed are
themselves decisions: D-129 (semantics owns the diagnostic contract),
D-001 and D-140 (parse codes), D-144 (seeds and shrinking), D-153 and
D-212 (refinement identity).

## All decisions

| Id | Document and section | Rule | Rationale |
| - | - | - | - |
| D-001 | `grammar.md` §introduction (D59) | Lexical/syntax diagnostics carry the semantics 9.4 `parse` code, a message beginning with the quoted text (D-238), span (for a lexical error about part of a token, that part), and the `expected`/`found` fields of generic messages; a failed file yields exactly one diagnostic, the earliest error (D-226). | One diagnostic per file is deterministic across implementations, and a recovery heuristic produces implementation-specific cascades that agents would have to learn to ignore; one code catalogue, owned by the document that defines every other diagnostic (semantics S60), is what lets a shared negative corpus match codes exactly. |
| D-002 | `grammar.md` §1.1 Source text (D1) | Comments may contain non-ASCII. | The design restricts identifiers to ASCII and makes strings Unicode but says nothing about comments; prose for human readers should not be constrained. |
| D-003 | `grammar.md` §1.2 Comments (D60) | `////` is an ordinary comment. | The design says documentation comments start with `///` (line 44) and does not address longer runs; `////`-style banner and separator lines are common, and treating them as documentation would put them into the `docs` facet and change its content version. |
| D-004 | `grammar.md` §1.3 Identifiers (D2) | Identifier case classes are enforced by the parser via `UPPER_IDENT`/`LOWER_IDENT`. | The class is load-bearing in two places where a lint would be too late: a bare `UPPER_IDENT` in a pattern is a nullary constructor while a bare `LOWER_IDENT` is a binding (`Err(Unavailable)` versus `Err(e)`), and `UPPER_IDENT "{"` in expression position is a struct literal. |
| D-005 | `grammar.md` §1.3 Identifiers (D61) | Annotation, hole, change, task, and `after` names are `LOWER_IDENT`; annotation arguments are literals. | The outline (design lines 617-619 and 626-629) is abbreviated and has one `identifier` class throughout, while the examples are uniformly snake_case in these positions; fixing the class gives the same deterministic reading D2 gives everywhere else, and an expression argument to an annotation would need a place in the dependency graph that the design does not describe. |
| D-006 | `grammar.md` §1.4 Keywords (D3) | `requires ensures effects invariant decreases using where forall assert` are reserved. | They begin continuation lines (Section 2.4) or statements, and an agent reading `ensures = 3` should never have to decide whether `ensures` is a variable. |
| D-007 | `grammar.md` §1.4 Keywords (D4) | `as async await break continue ghost lemma loop` reserved for future editions. | Only three are grounded in the design, which names ghost assertions as a later extension of the verified subset (line 100) and says host-level scheduling "does not add application-level `async` syntax to the initial CPL language" (line 461), so `ghost`, `async`, and `await` are spellings a later edition is likely to claim; `as`, `break`, `continue`, `lemma`, and `loop` are reserved by this specification on its own account, as the spellings import renaming, loop control, and named proof lemmas would most plausibly take, not because the design mentions them (it does not). |
| D-008 | `grammar.md` §1.4 Keywords (D5) | Work vocabulary is contextual, `.work`/`.patch` only. | `add`, `base`, `target`, `write`, and `task` are common value names in ordinary code, and the `.work` grammar is position-driven (LL(1)) so no ambiguity arises. |
| D-009 | `grammar.md` §1.5 Literals (D6) | Int literals are decimal only. | 0.1 exposes only arbitrary-precision `Int` at the surface; hexadecimal and binary forms matter for machine-width types that have no surface syntax yet. |
| D-010 | `grammar.md` §1.5 Literals (D7) | Text literals are single-line. | The layout algorithm (Section 2) is line-local, and diagnostics map lines to statements. |
| D-011 | `grammar.md` §1.5 Literals (D62) | Control characters excluded from `TEXT` are ASCII C0 (except tab) and DEL. | The exclusion stays within ASCII, so the lexer needs no Unicode category table and the rule is the same on every platform; non-ASCII content is the design's "strings are Unicode" and is not inspected further. |
| D-012 | `grammar.md` §1.5 Literals (D8) | No Bytes literal; identifier or keyword directly before `"` is an error. | Bytes values come from the prelude and adapters, and making an identifier directly before `"` an error keeps a future `b"..."` form from changing the meaning of code that lexes today. |
| D-013 | `grammar.md` §1.5 Literals (D9) | The Unit value is the prelude constructor `Unit`. | The design says the prelude supplies `Unit` "and their constructors", and `()` would introduce tuple-like syntax CPL does not have. |
| D-014 | `grammar.md` §1.7 The `?` rule (D10) | `?` adjacent to an identifier is a `HOLE` token; the name is snake_case and not a keyword. | The design calls the hole "a separate grammatical form"; deciding it in the lexer keeps the expression grammar free of a prefix/postfix conflict (`x?` versus `?x`). |
| D-015 | `grammar.md` §2.3 Statement termination (D11) | No operator or leading-dot line continuation; brackets and a header's `{` only. | The design says long contract expressions use explicit parentheses, and a single rule ("a line is a statement unless a bracket is open or the next line is a header's `{`") is what both agents and the formatter can apply with at most the one token of lookahead that Section 2.4 rule 3 already needs. |
| D-016 | `grammar.md` §2.4 Header continuation lines (D12) | `else` on the same line as the preceding `}` where newlines are significant. | After `}` a `NEWLINE` ends the `if` statement, and permitting `else` on the next line would require the parser to reopen a finished statement; this is Go's rule and it keeps "newline terminates" absolute. |
| D-017 | `grammar.md` §2.4 Header continuation lines (D63) | `{` may start the line after any header (`NEWLINE? block`). | The design's grammar outline writes `function = ... type, [effects], contract*, block` with its `newline` symbols only as clause terminators; it writes none between `type` and the first `ensures` of the `paginate` example either, so it is silent on layout between a header and what follows, not in conflict with the `paginate_ints` example (design lines 566-570), which puts `{` alone on the line after the return type with no clauses. |
| D-018 | `grammar.md` §3.1 Source file and module header (D13) | `use` declarations precede all other declarations. | Imports are the module's interface dependencies and tooling reads them without parsing bodies. |
| D-019 | `grammar.md` §3.1 Source file and module header (D14) | A module has no top-level `let`, `var`, or constant declarations. | The design excludes hidden mutable globals and never shows a module-level value. |
| D-020 | `grammar.md` §3.2 Imports (D15) | Single-item `use a.b.c` is allowed. | The design shows only the list form but the single form is the obvious degenerate case and costs the parser one lookahead. |
| D-021 | `grammar.md` §3.2 Imports (D16) | No `as`, no glob imports, non-empty use lists. | Explicit names keep the semantic index's dependency edges exact; `*` is the `.work` namespace selector, not an import form. |
| D-022 | `grammar.md` §3.3 Declarations and annotations (D17) | Annotation grammar open (`LOWER_IDENT` or keyword name, D-227), vocabulary closed at check. | The annotation set is tooling vocabulary that will grow; parsing must not fail on a newer edition's file before the checker can say which edition is needed. |
| D-023 | `grammar.md` §3.5 Type declarations (D64) | `type A = T` requires `where`; no transparent aliases. | The design shows exactly two `type` forms, the nominal wrapper `type PageId(Text)` and the refinement `type Positive = Int where self > 0` (lines 53-54), and states that an ordinary `Text` is not a `PageId` (line 75); a transparent alias would add a notion of type equivalence the design does not have. |
| D-024 | `grammar.md` §3.5 Type declarations (D18) | Wrappers have exactly one payload type. | The design's wrapper is a single-field newtype constructed `PageId("...")`; several fields belong in a `struct`. |
| D-025 | `grammar.md` §3.6 Structs (D65) | No per-field or per-variant `pub`. | The design's sentence "Public struct fields and enum variants are accessible through their exported type in this initial design" (line 71) can be read as "the fields of a public struct are reachable through it" or as "fields marked `pub` are"; its examples never write `pub` on a member, so the reading without per-member visibility is the one its text exercises, and it keeps the member grammar to one form. |
| D-026 | `grammar.md` §3.6 Structs (D19) | `struct`/`enum` accept generic parameters (and std's definition-less `type`). | The prelude's `List<T>`, `Option<T>`, and `Result<T, E>` are generic data types, and a user type with the same shape should not need a different grammar; whether the 0.1 typechecker supports user generic types is for the semantics specification, and a clear "not supported" there is better than a parse error here. |
| D-027 | `grammar.md` §3.7 Enums (D20) | Positional variant payloads only. | The design's variants are positional and the pattern grammar (3.13) is then one form. |
| D-028 | `grammar.md` §3.8 Capabilities (D21) | Capability operations may carry contracts. | The design says adapter contracts "are assumptions unless independently verified", which presupposes a place to write them. |
| D-029 | `grammar.md` §3.9 Functions (D66) | Clauses parse in any order; the formatter restores the outline's order. | The design's outline fixes `[effects], contract*` (line 613) and invariants before `decreases` (lines 623-624), and line 634 says contracts "are ordered requires clauses followed by ensures clauses in canonical output", which makes the outline's order a canonical-output rule for the contract clauses; applying the same parse-any-order, format-canonical treatment to `effects` and `decreases` gives one rule for all clauses. |
| D-030 | `grammar.md` §3.9 Functions (D22) | `fn` headers may carry `decreases`. | The design's prose says a recursive verified function declares a decreasing measure, which needs a place in the syntax; an annotation would make the measure a literal rather than an expression. |
| D-031 | `grammar.md` §3.9 Functions (D23) | Effect refs are `param.op`, no wildcards. | The design's bound is per handle and per operation; a wildcard would widen bounds silently. |
| D-032 | `grammar.md` §3.10 Tests and properties (D67) | Tests and properties take no `pub`. | The design says tests "live in namespaces like ordinary declarations" (line 285) and that declarations are private unless `pub` (line 71), but a test is never imported or called from source; it is addressed by tooling through selectors (`test(tests.pagination.*)`), so visibility would have no meaning for it. |
| D-033 | `grammar.md` §3.11 Blocks and statements (D24) | `let _ =` is the discard form. | Because non-tail expression statements must be `Unit`, an explicit discard form is required, and `_` is already the wildcard. |
| D-034 | `grammar.md` §3.11 Blocks and statements (D25) | Single-name `let`/`var`, no destructuring or compound/field assignment. | One binding form keeps the formatter and the hole diagnostics ("visible bindings") simple; `match` destructures. |
| D-035 | `grammar.md` §3.11 Blocks and statements (D26) | `return` is a statement, never an expression. | `?` covers the common early-exit, and keeping `return` out of the expression grammar means every expression has a value. |
| D-036 | `grammar.md` §3.11 Blocks and statements (D27) | `assert` takes one expression, no message. | The structured diagnostic already carries the expression text, location, and bindings. |
| D-037 | `grammar.md` §3.11 Blocks and statements (D28) | No bare block expressions. | It would collide with the struct-literal rule (Section 5 (a)) after a name on the previous line and adds scoping with no design motivation. |
| D-038 | `grammar.md` §3.12 Expressions (D29) | Spread is first and unique in struct literals. | The design writes `Page { ..page, text: trim(page.text) }`; fixing the position makes "base then overrides" readable in one direction. |
| D-039 | `grammar.md` §3.12 Expressions (D30) | No field punning, no type args on struct literals. | `name: expr` is one explicit form, and dropping `<...>` before `{` removes a second speculative parse. |
| D-040 | `grammar.md` §3.12 Expressions (D31) | Call-site `using` takes an expression. | Capabilities are forwarded from parameters and fields; a restriction to bare names would be arbitrary. |
| D-041 | `grammar.md` §3.12 Expressions (D32) | There are no closures, lambdas, or function values. | The design never shows one and effect tracking through the call graph is simplest with named callees. |
| D-042 | `grammar.md` §3.13 Patterns (D33) | Minimal pattern language. | The design's patterns are constructors, literals, bindings, and `_`; exhaustiveness checking is then a product of finite constructor sets, and the semantic patch grammar does not need to understand richer patterns. |
| D-043 | `grammar.md` §4.1 Work file (D34) | One or more `change` per `.work` file, each name unique across the project, which the coordinator enforces when it resolves a change by name (Milestone 6); nothing checks it in Milestone 1. | The CLI addresses changes by name, not by file. |
| D-044 | `grammar.md` §4.1 Work file (D35) | `git("ref")` is the only ref form; `target` must name a branch. | The design resolves `base` to a commit object id when the change opens; other version-control systems have no design. |
| D-045 | `grammar.md` §4.2 Tasks (D68) | Task requests are the `write`/`add` sets; host-resource grants come from project policy. | The design says "Task declarations request capabilities within the submitter's authorization" (line 361) and that granted permissions are "the intersection of project policy, the submitter's authority, and task requests" (line 367), but its `.work` example and its outline (`task_item*`) show no request item beyond the edit scopes; the edit scopes are the requests this grammar can express, and a request vocabulary for host resources belongs with the coordinator's sandbox design, which the design leaves to enforcement ("Merely parsing a declaration does not sandbox an agent", line 361). |
| D-046 | `grammar.md` §4.3 Integration (D36) | Closed requirement set of six forms, including `no_unresolved_assumptions`; any other token after `require` is `unknown_requirement` (a reserved word is `reserved_word`), and `require` with nothing after it is the generic `syntax_error`. | The integration policy is frozen per run and is the security boundary of a change; a closed grammar means a stale or malicious `.work` file cannot name a requirement the integrator silently ignores, and the design's own words place assumption strictness among the integration requirements rather than in `cpl.toml`, which admits assumptions but does not reject them. |
| D-047 | `grammar.md` §4.4 Selectors (D37) | Trailing facet-name segment is always the facet. | Facet names are the fixed vocabulary of the semantic index and selectors must parse without name resolution. |
| D-048 | `grammar.md` §4.4 Selectors (D38) | Bare selector = `.definition`; `*` is a namespace wildcard covering submodules (T43), never a facet wildcard (`paginate.*` is an error when `paginate` is a declaration and no module exists under the path, D-263); `add` sets take wildcards only. | The design writes `prove(paginate)` and `Positive.definition` side by side with the same meaning for the declaration as a whole. |
| D-049 | `grammar.md` §4.4 Selectors (D69) | Tests are selected only through namespace wildcards. | The design addresses tests only as `tests.pagination.*` (lines 330, 342) and requires a test selector to match at least one test (line 421); a `TEXT` segment would be the one selector form that is not an identifier path. |
| D-050 | `grammar.md` §4.5 Patch file (D39) | Patches target `body`, payload is a block, `expect base(...)` mandatory; other facets change by worktree edits. | The design's outline gives the patch exactly one payload production, `block` (lines 630-631), and a block can replace only a body; its example (389-411) and prose (413) describe body replacement with an exact facet-version check. |
| D-051 | `grammar.md` §4.5 Patch file (D40) | `.patch` is the patch file form and holds only patch forms. | The design names only `.cpl` and `.work` as file forms (line 7) and describes the patch only as content a candidate "can contain" (line 387), so where its text lives is undecided; a file of its own keeps the submission artifact separate from the work declaration, which is frozen for the run (line 351), and its selectors take their scope from the submitting task's change (Semantics above), not from imports of its own. |
| D-052 | `grammar.md` §5 (a) (D41) | Struct literals disabled in header expressions; flag restored before the header's `{`. | This is Rust's rule: it needs no lookahead and keeps `{` after a header unambiguous. |
| D-053 | `grammar.md` §5 (b) (D42) | Speculative generic-call parse, authoritative when it succeeds; bounded by the line only where newlines are significant. | Speculation is bounded by the type grammar and, outside insignificant-newline contexts, by the line, and the design spells generic calls `check<Positive>(n)` with no turbofish. |
| D-054 | `grammar.md` §5 (d) (D43) | One member-access form; property/method decided by the type. | The design fixes the spelling of each member and the grammar should not encode a per-name table. |
| D-055 | `grammar.md` §5 (e) (D44) | Constructor resolution (variants and wrappers): expected type, then lexical scope incl. prelude, qualified always. | The design writes `Err(Missing(_))` unqualified, which needs expected-type resolution; the lexical fallback keeps `Missing(id)` usable where no type is expected yet; treating a wrapper as a one-constructor type gives `PageId(t)` the same rule in expressions and in patterns (3.13). |
| D-056 | `grammar.md` §5 (f) (D45) | `forall` extent and placement. | The design writes exactly that example and a maximally extending prefix form must not be a left operand. |
| D-057 | `grammar.md` §5 (g) (D46) | `if` is always an expression. | One production serves both uses; the typechecker, not the grammar, demands an `else` and compatible branch types when the value is used, as the design states. |
| D-058 | `grammar.md` §5 (i) (D47) | `return` may omit its value, which is permitted only in a `Unit`-returning function. | `Unit` functions (`-> Result<Unit, E>` aside) need an early exit too. |
| D-059 | `grammar.md` §5 (j) (D48) | Negative literals via unary minus; folded only in patterns. | Lexing `-5` as one token would break `a-5`, while pattern position needs a literal form for negative constants. |
| D-060 | `grammar.md` §5 (k) (D49) | `else` may be followed by another `if`, giving `else if` chains with a single final `else`. | The design shows `if` and `else` only; chains are the universal expectation. |
| D-061 | `grammar.md` §5 (l) (D50) | `result`/`self` contextual identifiers. | Reserving `result` would reject a design example; contextual meaning is exactly what the design describes ("named `result`"). |
| D-062 | `grammar.md` §5 (m) (D51) | A block may be empty and then has value `Unit`. | `if c {}` and placeholder bodies should not need a dummy expression. |
| D-063 | `grammar.md` §5, further rulings (D52) | `_` wildcard token vs `_x` identifier. | Rust's convention, and the only `_` the design uses is the pattern wildcard. |
| D-064 | `grammar.md` §5, further rulings (D53) | Member names are never keywords. | Keyword escapes such as `r#type` would add a second identifier syntax; the only keyword a member position ever needs is the facet `effects` in selectors. |
| D-065 | `grammar.md` §5, further rulings (D54) | `..` appears only as the struct-literal spread; there are no range expressions or patterns. | Ranges have no design motivation and `..` is already taken by the struct-literal spread. |
| D-066 | `grammar.md` §5, further rulings (D55) | Match arms separated by newlines only. | The design shows no commas and states "one statement per line". |
| D-067 | `grammar.md` §5, further rulings (D56) | `test` reserved, `tests` ordinary. | `test` begins a declaration and must be reserved, while the design's own module path `tests.pagination` must stay a valid identifier path. |
| D-068 | `grammar.md` §6, corpus notes (D57) | Corpus prelude assumptions (Design conflict with design line 71), confirmed by stdlib 1.1 and semantics 1.7. | The design's examples use `flatten`, `check`, `ConstraintError`, and `gen` with no import, and the library specification places them in the prelude, so the corpus needs no glue `use` lines. |
| D-069 | `grammar.md` §6, corpus notes | Design conflict: design line 71's prelude list omits `flatten`, `check`, `ConstraintError`, and `gen`, which the design's examples use without imports; the corpus keeps the examples' text and resolves the conflict in favour of the examples. | The grammar parses identically either way, so the choice binds only the library specification, which owns the prelude's final content. |
| D-070 | `grammar.md` §6, corpus notes (D58) | `parse_size` glue via `std.text.parse_int`. | A body that executes keeps the `reader` project free of holes, which the `holes` project exists to exercise. |
